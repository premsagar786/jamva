SecureID: an Identity & Access Management backend skeleton

The repo is one thing: a hardened IAM spine. Stateless JWT auth, refresh-token rotation with replay detection, lockout and rate limiting stubs, RBAC-ready security config, a six-migration PostgreSQL schema, and a Docker + CI pipeline. What is not here yet is the business layer that sits on top of it — the auth, risk and admin controllers are specified in the docs, not implemented.

What is real in this repo

Verifiable from the source tree. The docs describe more than this; trust the file list, not the prose.

Running code implemented

  • JwtService — HS256 signing and parsing, access + refresh generation; refuses to start if JWT_SECRET < 32 chars
  • JwtAuthenticationFilter — Bearer extraction, signature/expiry check, fills SecurityContext (subject = user id, authorities = roles); 401 on expired tokens, fail-closed on malformed ones
  • SecurityConfig — stateless sessions, explicit permit-all list, BCrypt strength 12, hardening headers (CSP, HSTS, frame/content-type policy)
  • CorsConfig — origin allowlist with credentials, exposes Authorization and rate-limit headers, maxAge 3600
  • ApiResponse, ErrorCode, GlobalExceptionHandler — JSON envelope with typed error codes (423 ACCOUNT_LOCKED, 429 RATE_LIMITED, 401 TOKEN_REUSE_DETECTED)

Written, not running spec’d

  • All /api/auth/*, /api/users/*, /api/sessions/*, /api/admin/* endpoints — documented in docs/API.md; no controllers, entities or services yet
  • Risk engine — weights and thresholds configured in application.yml; the evaluation logic does not exist
  • Refresh-token reuse detection — the error code exists; the check does not
  • Redis rate-limit / lockout counters — keys and limits are specced; the code is a stub

The database is the part that is most finished

Flyway V1–V6 run on startup and create everything the planned business layer expects:

  • V1__create_users_table.sql — users, pgcrypto UUIDs, lower-cased unique email index, updated_at trigger
  • V2__create_roles_and_user_roles.sql — roles plus seed ROLE_USER / ROLE_SUPPORT / ROLE_MANAGER / ROLE_ADMIN
  • V3__create_tokens_tables.sql — refresh tokens stored hashed (SHA-256), revocable, replaced_by chain
  • V4__create_sessions_table.sql — sessions with device / ip / user-agent; the FK from refresh_tokens is added post-creation
  • V5__create_audit_tables.sql — audit_logs with JSONB + GIN index, plus login_attempts
  • V6__create_oauth_accounts.sql — Google accounts, unique per (provider, provider_user_id)

How a login is supposed to work

The intended design, as specified. The filter chain is implemented; the login endpoint that feeds it is not.

Access token engine implemented

Short-lived JWT, 15 minutes by default. Claims: sub (user id), email, roles, iss, iat, exp. Revalidated on every request by the filter. HS256 in dev (JWT_SECRET); RS256 is the prod plan via keypair.

Refresh token logic to build

32-byte secure random, stored hashed in Postgres. 7 days. One-time use: every refresh rotates it and marks the old row revoked with replaced_by pointing at the new one. The schema is built for this; the rotation service is not.

Refresh rotation exists for one reason: stolen tokens

Access tokens expire in 15 minutes, so a thief’s window is short. The refresh token is the long-lived key to the account — which is why it is one-time-use, and why replaying it is treated as a breach, not a bug.

The real-world version

You sign in to your bank on a shared laptop. Someone who had access to that machine later tries to use the saved session. With rotation, the moment they refresh a token that is already spent, the server can flag TOKEN_REUSE_DETECTED — it knows exactly which device that token belonged to, and it can kill that session and the rest of the chain before any of it is usable again. The attacker never gets a second token.

Account defense: what stops brute force

Two mechanisms, both designed around Redis (not yet implemented). One throttles the attacker; the other protects a legitimate user from being locked out by a throttler that only watches IPs.

Login rate limit stub

Key rate-limit:{endpoint}:{ip|email}, fixed window, 60 s TTL. Per-endpoint budgets from application.yml:

  • login 5/min
  • register 3/min
  • forgot-password 3/min
  • refresh 10/min

Over budget → 429 RATE_LIMITED with a Retry-After header.

Account lockout stub

Key login:failed:{email}, incremented per failed password and TTL’d 15 minutes. After 5 failures the account is locked for 15 minutes — regardless of which IP the attempts came from.

The lock is per-email, not per-IP: an attacker hammering from a new proxy every minute still hits the wall, and a user at a shared office NAT doesn’t get collateral damage.

The real-world version

Someone scrapes a leaked password list and sprays your company’s login page from a botnet. Every wrong guess hits Redis: the IP gets throttled at the HTTP layer, and the account accumulates failed attempts. At 5 failures the account locks for 15 minutes and a refresh of the page tells you to wait. The attacker moves on; smelling like a lockout is cheaper than a real breach.

Risk engine: scoring a login before trusting it spec’d

Each login adds penalty points from the evaluation, and the total picks a defensive policy. Weights and thresholds are already in application.yml; the engine that applies them is not.

Signal weights

  • New device +20 — user-agent differs from session history
  • New geographic location +30 — country not seen in the last 30 sessions
  • Impossible travel +40 — velocity between last login and this one exceeds ~800 km/h
  • Unusual access hour +10 — outside the user’s normal windows
  • Recent failed attempts +20 — Redis still holds failed state for this email

Escalation by score

  • < 30 — low, allow authentication
  • 30 – 60 — medium, require MFA / email OTP
  • 60 – 100 — high, block request, notify account by email
  • ≥ 100 — critical, lock account 15 min, revoke all sessions
The real-world version — "impossible travel"

Your account logs in from London, then 10 minutes later a request arrives that fingerprints as Tokyo — roughly 9600 km away. The implied velocity is tens of thousands of km/h, orders of magnitude over the ~800 km/h threshold the engine treats as impossible. That login is flagged +40. A legitimate traveller’s first login from the new country looks like a “new location” (+30) instead, which is exactly the case where the system asks for an email code rather than blocking outright.

what a migration guarantees
V3__create_tokens_tables.sql (abridged, from the repo)
CREATE TABLE refresh_tokens (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id     UUID REFERENCES users(id) ON DELETE CASCADE,
    token_hash  VARCHAR(64) UNIQUE NOT NULL,
    session_id  UUID,
    expires_at  TIMESTAMP NOT NULL,
    revoked     BOOLEAN DEFAULT FALSE,
    revoked_at  TIMESTAMP,
    replaced_by UUID
);

Only the hash of a refresh token is ever stored. The raw token is shown to the client once and spent on use — the DB never holds a usable session secret.

Run it

Docker is the recommended path. Everything in docker-compose.yml: API, Postgres 16, Redis 7, and MailHog for local email.

whole stack
$ cp .env.example .env
$ docker compose up --build

What comes up

  • API — http://localhost:8080
  • Health — /actuator/health (and metrics, prometheus exposed)
  • Swagger UI — /swagger-ui.html, spec at /v3/api-docs
  • Postgres — port 5432 · Redis — port 6379
  • MailHog UI — http://localhost:8025 (SMTP 1025)

Env that matters

  • JWT_SECRET — ≥ 32 chars, dev only
  • DATABASE_URL / USERNAME / PASSWORD
  • REDIS_HOST / REDIS_PORT
  • CORS_ORIGINS — allowlist, never * with credentials
  • FRONTEND_URL, GOOGLE_CLIENT_ID/SECRET, MAIL_*

The API boots and Flyway applies V1–V6. There are no controllers wired yet, so most routes return 404/401 from the security layer — that’s the current milestone boundary, not a broken install.

Deployment notes

From SECUREID_REPORT.md, condensed. Both playbooks run the same docker-compose stack behind a reverse proxy.

AWS — EC2 t3.micro (12-mo free tier)

  • Ubuntu 24.04, security group: 22 (your IP), 80, 443
  • apt install docker.io, add user to docker group
  • clone, cp .env.example .env, set prod values, docker compose up -d --build
  • Nginx reverse proxy 80/443 → localhost:8080; certbot --nginx for TLS

GCP — Compute Engine e2-micro (always free)

  • Region us-central1 / us-east1 / us-west1, 30 GB standard disk
  • Create VPC firewall rules for TCP 80/443 from 0.0.0.0/0
  • Same clone + .env + docker compose up -d --build

Prod-only env differences: SPRING_PROFILES_ACTIVE=prod, real SMTP, explicit CORS_ORIGINS, RS256 via JWT_PRIVATE_KEY/PUBLIC_KEY, and a real secret. Report has the full step-by-step for both clouds.
